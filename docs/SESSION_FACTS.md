# Сохранение истории повторных партий при объединении аккаунтов

Подготовлено 11 сентября 2026. **Код проверен локально; production-выпуск этой доработки пока не подтверждён.** Не путать с уже выпущенным утром `b6bd73f4`.

## Что исправлено

При связывании гостя с существующим аккаунтом профиль по-прежнему оставляет более продвинутый результат одной ежедневной задачи. Но удаление дубликата больше не должно уничтожать аналитическую историю реально сыгранных партий.

Миграция `0054_preserve_game_session_facts` вводит `game_session_facts`. Это минимальные серверные факты игрового эпизода: исходный UUID, владелец, режим/тип, начало, первое завершение, исходная партия, способ доступа и этап эксперимента. Здесь нет email, имён, IP, ответов игрока, OAuth-токенов или клиентского first-touch. Согласия и клиентская аналитика не меняются.

- `id` и `source_session_id` намеренно не ссылаются внешним ключом на удаляемые строки `game_sessions`.
- Триггер атомарно с игровым действием фиксирует начало и первое завершение. Перезагрузка, смена владельца, FK SET NULL или позднее присвоение источника не переписывают исходную хронологию/атрибуцию.
- При merge перед удалениями блокируются игровые строки обеих сторон, затем выполняется прежнее объединение. После него все факты гостя, включая удалённые дубликаты, переходят целевому аккаунту.
- Настоящее удаление владельца удаляет его факты каскадно. Отдельные факты после дедупликации сохраняются, пока существует владелец, как история его игры.
- Исходная политика выбора результата, награды, кошелёк, цены, доступ, SEO и экспериментальные флаги не меняются.

Блокировки игровых строк перед фактами не добавляют инверсию «строка факта → игровая строка». Это не обещание устранения всех существующих конкурентных сценариев наград/авторизации: общий порядок их блокировок не перерабатывался.

## Отчёт роста

Версия определений: `linked-repeat-v3-episode-facts`. `/admin/economy#growth` считает игровые показатели из фактов реальных эпизодов, а не только из оставшихся после дедупликации результатов профиля.

Для повторов сохраняется прежняя узкая когорта: прямые продолжения первой измеренной завершённой партии пользователя в выбранном окне. Дополнительно проверяются:

1. Один и тот же объединённый владелец исходной и следующей партии.
2. Публичный тип «Диагнозов», не спецпакет.
3. Старт следующей партии не раньше фактического завершения исходной.
4. Завершение повтора не раньше его старта.
5. Завершённые UTC-дни и исключение администраторов.

Цепочка A → B → C полностью хранится, но в этой конкретной метрике после первой A прямым повтором считается B, а не все потомки. После объединения двух идентичностей число уникальных игроков и выбор первой партии могут измениться. Сохранение фактов не означает, что любые агрегаты обязаны оставаться прежними.

Новая версия сохраняет две действительно сыгранные партии, даже если в профиле остаётся один результат. Это изменение определения относительно старого отчёта, не искусственно созданные игры и не доказательство продуктового роста. Регистрации, оплаты и клиентские события остаются своими отдельными источниками.

## История до исправления

Миграция копирует только реально существующие строки с `origin=existing_snapshot`. Уже удалённые партии и потерянные связи не восстанавливаются догадками; `null` остаётся `null`. Новые записи получают `origin=live`.

Между копированием и установкой триггера записи `game_sessions` заблокированы в транзакции, чтобы не было пропуска. В `app_settings['analytics.gameSessionFacts']` сохраняется фактическая дата начала записи, не дата, зашитая в коде.

API возвращает `measurement.episodeFacts`:

- `recordingStartedAt` — дата миграции;
- `fullDaysFrom` — следующий полный UTC-день;
- `coverage` — `unavailable`, `legacy_partial`, `partial` или `complete` для выбранного окна.

Первоначальное начало измерения повторов 8 сентября не сдвигается. Новая граница — отдельный контроль сохранности при merge. Админка предупреждает о неполной ранней истории вместо заявления о полном покрытии. Отсутствие метаданных тоже не считается полным покрытием.

## Выполненные проверки

- 16 узких unit-тестов: управление этапами, границы измерения, выбор архивного продолжения и видимость предложений.
- 10 PostgreSQL integration-тестов: 6 новых сценариев merge/facts и 4 существующих сценария growth-report.
- Обе стороны удаления дубликата исходной партии, удаление самой повторной партии, цепочка из трёх, идемпотентность, перенос на аккаунт перед удалением гостя.
- Первое завершение, исходный старт/источник/доступ не меняются; позднее присвоение источника старой партии не засчитывается.
- Исключение чужого владельца, неверной хронологии, других режимов, админов, спецпакетов и текущего дня.
- Обычное удаление владельца очищает его исторические факты.
- Отдельная чистая БД проверила upgrade `0053 → 0054` на трёх синтетических существующих сессиях: точное сохранение дат/связей, неизменность игровых строк, сохранение неизвестной связи и последующий live capture.
- `npm run typecheck`, `npm run build:api`, `npm run build` и `git diff --check` прошли. Сборка сохранила 57 индексируемых страниц; новые SEO-правки не вносились. Сохраняются прежние предупреждения сборщика об отдельных runtime-ассетах и размере большого chunk.

Все БД для проверки отдельные, локальные, синтетические; Docker и production-БД не использовались. Никаких тестовых регистраций/покупок на сайте не создавалось. Полноценный браузерный merge под гостем на новой production-версии пока не выполнен.

## Порядок выпуска и контроль

1. Получить разрешение на production и проверить текущий SHA/состав изменений. Выпускать API/worker/миграцию вместе и обновлённую подпись админки, не web-only.
2. Сделать проверенный резервный снимок БД и сохранить текущие образы/конфигурацию для отката. Не импортировать игровой контент и не трогать активную ревизию.
3. Применять миграцию вместе с новой merge-реализацией. Не оставлять старый API после установки триггера: старый merge не переносит факты удалённых дубликатов. Начало полного post-release окна подтвердить по фактической активации API, особенно если выпуск пересёк полночь UTC.
4. Проверить journal `0054`, таблицу/триггер и метаданные; сравнить число существующих сессий и соответствующих им фактов, отсутствие потерь и дублей. Агрегаты до/после — только без PII.
5. Проверить совпадение web/API SHA, работоспособность игры/админки и предупреждение о старой истории. Все growth-флаги должны остаться прежними.
6. В 24–48 часов проверить новые записи и сохранность связей при реальных объединениях, не объявлять рост конверсии по изменению определения. Не восстанавливать несуществующую историю.

Добавочная таблица допускает сохранение схемы при откате, но старый код не обеспечивает новое свойство. Предпочтителен исправляющий релиз вперёд; при возврате старой авторизации контроль сохранности надо снова обозначить как неполный. Автоматически удалять новую таблицу или восстанавливать весь production из backup нельзя.
