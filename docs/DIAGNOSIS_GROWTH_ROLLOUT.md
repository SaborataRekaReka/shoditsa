# Диагнозы → повторная игра → регистрация → клуб

Подготовлено 7 сентября 2026. Основание: полный аудит 07.09, а не гипотеза о дефиците SEO. За последние 7 завершённых дней: 72 старта и 54 завершения Диагнозов в общей серверной активности; consented organic cohort — 16 входов / 12 стартов / 6 завершений / 1 следующий старт. Выборка органики мала. За 05–06.09: 17 завершений / 5 связанных переходов в другие игры, в органике 2 / 0. Это baseline, не эффект нового сценария.

## Выпуск и последовательность

Штатный единый release из main (web/API/worker), миграция `0052_diagnosis_growth_funnel`. Никаких новых карточек, AI-генераций, SEO-текстов, цен и прав действующих подписок.

Сразу: Яндекс выше email-формы; выбор тарифа гостем измеряется до регистрации; условия и автопродление не выбраны заранее; параметр `product` больше не запускает checkout автоматически. После входа пользователь подтверждает покупку сам. Сохраняются тариф, непрозрачный intent и allowlisted контекст Диагнозов; после подтверждённой оплаты есть возврат к игре.

Эксперимент управляется в `/admin/economy#growth`, API `GET/PATCH /api/v1/admin/growth`. Setting `growth.diagnosisContinuation`, аудит изменений. По умолчанию `baseline`, автоматического календарного включения нет.

1. **baseline:** сохранить чистое окно рекомендаций 05–11.09. Решение 12.09 по действующему SEO-плану.
2. **replay:** основная кнопка «Следующий случай», видимая стоимость до списания, другие игры вторичны. Не раньше 12.09. Измерять первый завершённый результат игрока в окне → связанный повторный старт → завершение повтора. Операционные ориентиры: 30/100 продолжили, 20/100 завершили вторую; при малой выборке показывать абсолютные числа, не обещать эффект.
3. **registration:** только после оценки минимум 7 полных UTC-дней replay. Новому аккаунту один раз выдаются 3 дополнительные партии Диагнозов. Это не валюта: нельзя потратить на AI, Данетки, другие игры или покупки. Ориентир 10 новых аккаунтов на 100 действительно увиденных предложений — гипотеза, не прогноз.
4. **club:** после отдельного окна регистрации. Контекстное предложение при недостатке билетов или после нескольких игр, 30 дней первичны, год вторичен. Цена берётся из публичного серверного каталога (на baseline 199 ₽ / 30 дней); никаких скидок или включения скрытых ticket bundles.

Админ должен явно отметить, что проверил предыдущий этап. Сервер не разрешает пропуск этапов и переход раньше семи полностью завершённых UTC-дней после включения. Немедленная пауза разрешена. Уже выданные бонусы при паузе сохраняются; активный клуб не расходует бонус.

## Источники истины и ограничения

- `registration_play_credits`: одна строка на новый аккаунт, remaining 0–3; grant вызывается при фактическом создании неанонимного user. Повторный вход не вызывает начисление.
- Списание бонуса, запуск игры и обновление кошелька/usage — одна транзакция. Повтор одного idempotency key возвращает ту же сессию; параллельные запросы не дают четвёртой бонусной партии. Бонус не повышает платную дневную лестницу.
- `game_sessions.access_source`, `source_session_id`, `growth_stage`: серверные источники повторов и использования льготы. Source session проверяется на владельца, тот же режим, завершение и отсутствие спецподборки. Старые NULL не backfill и не считать нулём поведения.
- `completions` — все результаты (в том числе проигрыш/раскрытие), `firstCompleters` — игроки с результатом в окне, `repeatingCompleters` — те, кто продолжил после первого результата в этом окне. Это не все повторные посетители проекта. `repeatStarts/repeatCompletions` связаны именно с этой первой сессией.
- Бонус: `bonusGranted/bonusPlayers` — когорта выдачи; `bonusStarts/bonusCompletions` — когорта запусков. Не делить разные когорты друг на друга.
- `accounts.created` — users.createdAt без анонимов/админов; signUps — серверная регистрация тех же аккаунтов, не sign_in и не legacy auth_success.
- Покупки — payment_orders, не клиентский purchase_succeeded; когорта по дате создания заказа. `paidUsersUsedClub` — игроки, использовавшие свободную игру после оплаты. Архив и AI-льготы в этот показатель не входят. Администраторы и stub исключены, другие тестовые покупки требуют ручной классификации. Нет автоматического вывода «первая реальная покупка».
- Новые client events перечислены в таблице ниже. Показ — элемент, видимый минимум на 25% (IntersectionObserver), не mount страницы; first-party eventId стабилен для session + stage.
- События проходят существующую модель согласия, first-touch не сохраняется при отказе. Админская таблица разделяет stage/consent. Метрика получает соответствующие reachGoal; наличие целей в live-каталоге подтверждать отдельно, не считать добавление кода созданием цели.
- intent_id связывает выбор тарифа гостем и авторизованный checkout; metadata заказа хранит intentId, placement, sourceMode. Это не деньги и не источник first-touch. Для атрибуции регистрации использовать consented acquisition/auth_events, не угадывать канал по контексту предложения.
