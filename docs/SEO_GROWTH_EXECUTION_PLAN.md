# План SEO- и продуктового роста shoditsa.ru

Дата базового среза: 19 августа 2026 года. Документ предназначен для ИИ-агента, который продолжает развитие проекта после трафикового аудита.

## Цель

Увеличить органические клики и регистрации без рискованных переписываний уже работающих страниц. Работать по воронке:

`спрос → показы → позиция → CTR → посадочная → старт → завершение → регистрация → следующая игра`.

Не считать задачу выполненной только по успешной сборке. Каждый релиз должен иметь техническую проверку, визуальную проверку в браузере и измеримый пост-релизный критерий.

## Проверенная исходная точка

- Google, текущие 14 завершённых дней против предыдущих: 333 против 211 показов; 65 против 45 кликов.
- Яндекс, номинальное окно 5–18 августа против 22 июля–4 августа: 574 против 162 показов; 90 против 48 кликов. Данные за 18 августа ещё не поступили, поэтому текущая половина фактически покрывает 5–17 августа и не трактует задержку как нулевой день.
- Данетки за 7 дней: 195 показов и 9 кликов против 44 и 1 ранее; это новый драйвер видимости, а не повод немедленно менять сниппеты.
- `/games/diagnosis`: основной доказанный драйвер; CTR около 24,4% в Google и 37% в Яндексе.
- `/games/character`: 45 показов Google при средней позиции 10,6 и 38 показов Яндекса без кликов. Точный Wordstat-запрос `!игра !угадай !персонажа` — 1 236 в месяц.
- Google Search Console на момент среза показывал 0 внешних ссылок.
- В SEO-манифесте 57 индексируемых URL; у всех проверенных страниц один H1, корректные canonical, robots и JSON-LD.
- Точная конверсия органики в регистрацию пока недостоверна: гостевые `client_events` могут удаляться при связывании аккаунта, а часть завершений и переходов между играми имеет неоднозначную семантику.

## Правила для агента

1. Перед любым новым SEO-изменением собрать свежий снимок через `$shoditsa-traffic-audit` и сравнить два завершённых окна 7/7 и 14/14.
2. Не считать отсутствующий или запаздывающий день нулём.
3. Не менять одновременно title, H1, description, первый экран и внутренние ссылки одной страницы: иначе невозможно определить причину результата.
4. Не переписывать canonical, robots, JSON-LD и общую архитектуру без конкретной ошибки в Вебмастере или Search Console.
5. Не создавать новую тонкую посадочную только из-за широкой частотности Wordstat. Нужны точный интент, самостоятельная ценность и достаточный контент.
6. Не публиковать ссылки на внешних площадках и не действовать от имени владельца без явно выбранных площадок и разрешения на публикацию.

## Этап 1. Обход и внутренний вес

### Изменения

- Добавить `/games/character` в постоянную навигацию/подвал рядом с остальными публичными играми.
- Сделать список игр на главной полным и основанным на едином источнике данных, а не на нескольких расходящихся хардкодах.
- Исправить расхождение «11 игр»/«12 игр» в статическом fallback и runtime-копирайте.
- В sitemap указывать `lastmod` только по реальной дате изменения URL. Если надёжной даты нет — опускать `lastmod`, а не ставить дату каждого деплоя.
- Сохранить текущие canonical, robots и structured data.

### Definition of Done

- В собранном HTML все публичные игры доступны минимум по одной обычной `<a href>`-ссылке с главной или подвала.
- `/games/character` присутствует во внутренней ссылочной структуре.
- Число игр формируется из одного актуального каталога или совпадает во всех поверхностях.
- Повторная сборка без изменения контента не меняет `lastmod` всех URL.
- `npm run build`, SEO-проверки и целевые тесты проходят.

### Метрика после релиза

- Через 7–14 дней: sitemap обнаруживает все опубликованные URL; `/games/character` появляется в Internal links.
- Через 2–4 недели: растёт число индексированных игровых/SEO-страниц без роста canonical-конфликтов.

## Этап 2. Достоверная воронка

### Изменения

- При `mergeAnonymousAccount` переносить `client_events` на зарегистрированного пользователя до удаления гостя.
- Сохранять связь `game_session_id` и не создавать дубликаты событий при конфликте `event_id`.
- Сделать завершение Данеток идемпотентным: повторный mount/reload завершённой комнаты не должен создавать новое `danetki_room_completed`.
- Разделить намерение и факт перехода:
  - `cross_game_clicked`/существующее специализированное событие — клик;
  - `game_next_start` — только подтверждённый старт новой серверной сессии.
- Передавать стабильный `transition_id`, `from_mode`, `to_mode`, entry path/source/search engine и непрозрачный `acquisition_id` там, где это допускает согласие и модель приватности.
- Хранить сырые события 38 завершённых дней для точного 31-дневного cohort-среза и отдельно архивировать обезличенные суточные activity-агрегаты старше 30 дней.

### Definition of Done

- Интеграционный тест доказывает, что pre-registration события остаются после связывания аккаунта.
- Reload завершённой Данетки не увеличивает число завершений.
- Один переход между играми даёт максимум один click и один фактический start с общим `transition_id`.
- Внутренняя статистика может показать по URL и игре: landing → start → complete → registration → next start за 7/14/31 день.

### Метрика после релиза

- Не менее 95% зарегистрированных после гостевой игры имеют склеенную pre-registration цепочку.
- Доля дублей completion по одному session id равна 0.
- Появляется базовая конверсия регистрации по органической посадочной; только после этого запускается CTA-тест.

## Этап 3. Тест роста `/games/character`

Сначала выполнить этап 1 и дать поисковикам минимум одну полную неделю. Не менять текущий title заранее.

### Условие запуска теста

- накоплено не менее 100 релевантных показов;
- средняя позиция не хуже 10;
- CTR ниже 2%.

### Единственное изменение теста

Сначала проверить H1 и первый экран: явная формулировка «Игра “Угадай персонажа”» и короткое объяснение механики. Не менять одновременно title и description.

### Успех

- CTR растёт минимум на 1 процентный пункт при сопоставимой позиции;
- start/landing не ухудшается;
- результат подтверждается хотя бы одним полным 14-дневным окном.

## Этап 4. Данетки

До контрольного среза 4 сентября 2026 года не менять titles, descriptions, URL, архитектуру и механику Данеток. Новые данетки в текущей задаче не генерировать.

Решение по комнате возможно только при ≥20 органических стартов, полном RAW-покрытии и сопоставимых когортах: вход → реальная комната (ориентир ≥40%), начатая комната → завершение (≥30%). Контентные просмотры и все события активности — отдельный контекст, не знаменатель этих конверсий.

Отложенные гипотезы после контрольного среза и отдельного решения по контенту:

- расширять существующие подборки `dlya-detey`, `slozhnye`, `legkie`, `novye` до 12–15 качественных сюжетов;
- приоритизировать страницы с устойчивыми показами, позицией 4–10 и достаточным start rate;
- не создавать отдельные «интересные» или «страшные» страницы, пока точный спрос и объём контента не оправдают самостоятельный URL;
- измерять story view → play click → room start → first question → completion → registration.

## Этап 5. Внешний авторитет

Это отдельная ручная/согласованная задача. Подготовить три типа посадочных ссылок:

- главная — описание всего проекта;
- `/games/character` — крупнейшая следующая семантическая возможность;
- `/danetki` — уже растущий кластер с самостоятельным контентом.

Получить первые 3–5 редакционных упоминаний на тематически подходящих площадках. Запрещены покупные сетки, массовые каталоги низкого качества, автоматический спам и одинаковые анкоры.

Успех через 4–8 недель: не менее трёх ссылающихся доменов, первые внешние ссылки в Search Console, рост позиций целевых URL.

## Что не трогать без нового сигнала

- SEO-сниппет `/games/diagnosis`.
- Canonical, robots и JSON-LD существующих 57 URL.
- Регион сайта и Яндекс Бизнес для глобальной онлайн-игры.
- Movie/Connections по единичной недельной волатильности.
- Music до ≥50 показов при позиции ≤8 и CTR <3%.
- Animals до накопления устойчивой выборки.

## Порядок проверки перед релизом

1. `git diff --check`.
2. Целевые unit/integration tests для изменённых модулей.
3. `npm run typecheck`.
4. `npm run build`.
5. Проверить сгенерированные sitemap и SEO HTML: URL, H1, canonical, robots, JSON-LD, внутренние ссылки.
6. В браузере на desktop и узком viewport пройти главную, `/games/character`, `/danetki` и регистрацию после гостевой игры.
7. Убедиться в отсутствии ошибок console/network.
8. После отдельного разрешения на продакшен — выпустить обычным проектным release-процессом и проверить production URL.
