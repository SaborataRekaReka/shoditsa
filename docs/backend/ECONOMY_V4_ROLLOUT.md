# Economy v4: rollout и rollback

## До включения

1. Сделать PostgreSQL backup и записать SHA релиза.
2. Применить миграции `0033`–`0035`.
3. Проверить, что в `economy_rule_sets` ровно одна активная версия и это v4.
4. Проверить club-only инвариант опубликованных спецпоказов: `access_model = club`, `included_in_club = true`, `preview_items = 0`, `product_id is null`.
5. Оставить `TICKET_BUNDLES_ENABLED=false`, пока не завершена отдельная платёжная приёмка.

## Постепенное включение

`ECONOMY_V4_ROLLOUT_PERCENT` задаёт процент стабильной выборки игроков от 0 до 100. Администраторы всегда получают активную версию. Назначение сохраняется в `economy_rule_assignments`, поэтому пользователь не прыгает между группами.

Рекомендуемый порядок: 5% → 20% → 50% → 100%. На каждом этапе проверить:

- ошибки `ECONOMY_RULES_UNAVAILABLE`, `INSUFFICIENT_TICKETS` и платёжные reversal;
- начисления и списания по `wallet_ledger.rules_version`;
- отдельные дневные счётчики free play, Friends Room и Данеток;
- долю завершений финальной сверки и продолжений Friends Room;
- отсутствие новых pack-заказов.

## Быстрый rollback

1. Установить `ECONOMY_V4_ROLLOUT_PERCENT=0` и перезапустить API.
2. Новые пользователи попадут в control v3; уже назначенные пользователи сохранят свою версию. Для аварийного массового переключения сначала зафиксировать incident и сделать backup, затем обновить назначения v4 на v3 отдельной аудируемой SQL-операцией.
3. Не удалять новые таблицы и колонки: старый API должен откатываться только на совместимый expand/contract релиз.
4. Не отменять уже записанные ledger-операции. Ошибочные начисления компенсировать новой `adjustment`-операцией.
5. Для наборов билетов достаточно установить `TICKET_BUNDLES_ENABLED=false`; оплаченные заказы и refund/chargeback продолжают обрабатываться.

Спецпоказы после rollback остаются club-only. Возврат платной продажи pack-продуктов не является частью rollback экономики v4.
